heapmap: a learned block-range index for PostgreSQL
   PostgreSQL 18.7 (Ubuntu 18.7-1.pgdg24.04+2) on x86_64-pc-linux-gnu, database hm_test
   An event log of 5000000 rows. Timestamps only move forward, as in any log.
   Three copies of the table, identical row for row, one index each.

== 1. Load the table
   | CREATE UNLOGGED TABLE ev_src AS
   | SELECT timestamptz '2026-01-01' + sum(1 + (random() * 2000)::int) OVER (ORDER BY i) * interval '1 millisecond' AS ts,
   |        (random() * 1000)::int AS device, random() AS reading
   | FROM generate_series(1, 5000000) i;
   | SELECT count(*) AS rows, min(ts) AS first_event, max(ts) AS last_event,
   |        pg_size_pretty(pg_relation_size('ev_heapmap')) AS table_size FROM ev_heapmap;
  rows   |          first_event          |          last_event           | table_size 
---------+-------------------------------+-------------------------------+------------
 5000000 | 2026-01-01 00:00:00.033+05:30 | 2026-02-27 22:30:16.185+05:30 | 249 MB
(1 row)


== 2. Build one index on each copy
   | CREATE INDEX ev_btree_ts ON ev_btree USING btree (ts);
   | CREATE INDEX ev_brin_ts ON ev_brin USING brin (ts);
   | CREATE INDEX ev_heapmap_ts ON ev_heapmap USING heapmap (ts);

                                              B-tree           BRIN        heapmap
                                              ------           ----        -------
   build time, one core (s)                     1.11           0.43           0.42
   index size                                 107 MB          24 kB          24 kB
   
   The B-tree stores every timestamp with a row pointer. BRIN stores a min and
   max per 128 table pages. heapmap stores a few line segments that say which
   table page each timestamp is on, and nothing per row.

   Each segment is a straight line from timestamp to table page. The window is
   how far a row can be from the line. A lookup reads only the pages in it:
   | SELECT first_page, last_page, scans_tail
   | FROM heapmap_window('ev_heapmap_ts', (extract(epoch FROM timestamptz '2026-01-29 23:02:02.898+05:30' - timestamptz '2000-01-01 00:00:00+00') * 1e6)::bigint);

== 6. Keep loading: 1000000 more rows into each table
                                              B-tree           BRIN        heapmap
                                              ------           ----        -------
   load time (s)                                0.97           0.43           0.52
   write-ahead log produced                   140 MB          77 MB          77 MB
   index size now                             129 MB          24 kB          24 kB
   
   A row that arrives in order costs heapmap nothing: the newest table pages
   are always searched, and every few pages the model is extended over them.

== 7. Rows that do not fit the pattern
   1,000 events arrive late, with timestamps from all over the past:
   | INSERT INTO ev_heapmap
   | SELECT timestamptz '2026-01-01' + random() * (timestamptz '2026-01-29 23:02:02.898+05:30' - timestamptz '2026-01-01') + interval '0.5 microsecond', -1, 0
   | FROM generate_series(1, 1000);
   Then the log carries on as usual, and the pages holding the late rows join the model:
   | INSERT INTO ev_heapmap
   | SELECT (SELECT max(ts) FROM ev_heapmap) + i * interval '1 second', 0, 0 FROM generate_series(1, 20000) i;
   exception entries: 119 before, 1119 after. Each late row is stored exactly, like a B-tree entry.
   | SELECT ts, device FROM ev_heapmap WHERE ts = '2026-01-04 01:17:04.215014+05:30';
                ts                | device 
----------------------------------+--------
 2026-01-04 01:17:04.215014+05:30 |     -1
(1 row)

   And a row whose timestamp is changed is still found under the new one:
   | UPDATE ev_heapmap SET ts = ts + interval '3 days' WHERE ts = '2026-01-04 01:17:04.215014+05:30';
   | SELECT ts, device FROM ev_heapmap WHERE ts = timestamptz '2026-01-04 01:17:04.215014+05:30' + interval '3 days';
                ts                | device 
----------------------------------+--------
 2026-01-07 01:17:04.215014+05:30 |     -1
(1 row)


== 8. 8 sessions inserting at once, for 12 seconds
   Every transaction adds the same event to all three tables. Growth of each index, live:
   second     rows added         B-tree           BRIN        heapmap
        2         164189       +3608 kB       +0 bytes    +8192 bytes
        4         337791       +7408 kB       +0 bytes         +24 kB
        6         515277         +11 MB       +0 bytes         +32 kB
        8         689024         +15 MB       +0 bytes         +48 kB
       10         871869         +19 MB       +0 bytes         +56 kB
       12        1022493         +22 MB       +0 bytes         +64 kB
   1022493 rows added to each table, 85259 transactions per second.
   
   Sessions inserting at the same time each fill a table page of their own, so
   neighbouring timestamps end up several pages apart. heapmap answers by reading
   a wider window for those timestamps, and stores exactly the few rows left over:
   | SELECT segments, max_window AS widest_window, tail_pages, exception_entries,
   |        round(100.0 * exception_entries / 7043493, 2) AS percent_of_rows, pg_size_pretty(index_bytes) AS size
   | FROM heapmap_stats('ev_heapmap_ts');
